# Exploration: OpenClaw — do we gain anything from it on this project?

> Stage: Explore | Date: 2026-03-23
> Pipeline: **Explore** → PRD → Architecture → QA → Plan → Value → Challenge → Decision

## Idea summary

Evaluate whether OpenClaw (open-source autonomous AI agent framework, 247k GitHub stars) offers meaningful value on top of the existing Macular Society RAG platform.

## What is OpenClaw?

OpenClaw is a locally-runnable autonomous AI agent daemon that wraps an LLM (OpenAI, Claude, DeepSeek) and exposes it across 12+ messaging platforms (WhatsApp, Telegram, Signal, Discord, Slack, iMessage, Teams, etc.). It ships with a skills system (directories containing `SKILL.md` metadata), persistent cross-session memory, a heartbeat scheduler, and voice note support on WhatsApp and Telegram.

Originally named Clawdbot (Nov 2025), renamed twice before settling on OpenClaw. Founder joined OpenAI in Feb 2026 and handed governance to an open-source foundation. Project stability is unclear.

## Codebase recon

- No existing OpenClaw references anywhere in the codebase.
- No prior exploration on related agent frameworks or messaging gateway topics.
- The project already has its own agentic loop: RAG pipeline with OpenAI function calling, contact collection state machine, streaming SSE, voice via Whisper + Piper.

## Problem interpretations

### Interpretation A: Messaging channel as an alternative access point

WhatsApp has deep penetration among older UK adults — a demographic that overlaps heavily with macular degeneration patients. Some users may find WhatsApp more familiar and comfortable than a browser-based chat. OpenClaw could put the RAG assistant inside the messaging app they already use daily.

### Interpretation B: Internal staff workflow automation

OpenClaw's agentic loop could run autonomous background tasks for Macular Society staff — drafting follow-up emails to collected contacts, summarising week's conversations, triggering CRM updates. This is unrelated to the patient-facing RAG pipeline.

### Interpretation C: Replacing or augmenting the agent framework

Use OpenClaw's scheduling, memory, and skills system as the backbone of the RAG pipeline instead of the bespoke NestJS agent loop. Frame it as accelerating future agentic features.

## Who is affected

| User | Situation | Current workaround | Pain level |
|------|-----------|--------------------|------------|
| Patient with macular degeneration | Prefers WhatsApp; browser-based UI is unfamiliar or harder to configure for accessibility | Uses phone with zoom/voice, or calls helpline directly | Med |

For macular degeneration users accustomed to their phone's accessibility settings, a WhatsApp interface could be more natural than the web app — but this is unverified._

## Why now

- OpenClaw is viral (247k stars) and the question of "should we use it?" is timely.
- The platform is approaching a maturity point where channel diversification is a plausible next step.
- Voice note support on WhatsApp/Telegram is notable — the project already invests in voice (Whisper STT, Piper TTS).

## Existing solutions

**Internal:**
- Custom NestJS RAG pipeline with OpenAI function calling — covers the agent loop already.
- Voice I/O via Whisper (STT) and Piper (TTS) — already handles voice interaction in the web app.
- Contact collection state machine — captures callback requests in-session.
- Session management, streaming SSE — all in-house.

**External:**
- OpenClaw: messaging gateway + agent daemon. Would sit _in front of_ the existing RAG API, not replace it.
- Alternatives: Botpress, Twilio Flex, WATI (WhatsApp Business API wrappers) — more mature, purpose-built for WhatsApp integration with less agentic complexity.

## Possible directions

### Direction A: WhatsApp/Telegram gateway only

Use OpenClaw as a thin messaging gateway that relays user messages to the existing RAG API and returns responses. Don't use its agentic capabilities at all — just the channel connectivity. Voice note → Whisper STT → RAG API → Piper TTS → voice reply in WhatsApp.

### Direction B: Ignore OpenClaw, build a direct WhatsApp integration

Use the WhatsApp Business API (Meta) or Twilio directly, without OpenClaw. More stable, more production-grade, no dependency on a fast-moving open-source project with unclear governance.

### Direction C: Staff-only OpenClaw instance for workflow automation

Deploy OpenClaw separately for internal Macular Society staff workflows (contact follow-up, conversation summaries, CRM updates). Completely isolated from the patient-facing system.

## Hard problems

- **Security model mismatch.** OpenClaw requires broad permissions (email, calendar, messaging platforms). A medical charity handling patient contact details cannot accept an agent with broad, loosely scoped access. Would need significant sandboxing.
- **Governance risk.** The project was renamed twice in 3 months. The founder joined OpenAI in Feb 2026. The open-source foundation handover is recent and unproven. Betting infrastructure on this is a risk.
- **Nothing to replace.** The existing stack already handles everything OpenClaw provides internally (agent loop, memory, voice, session management). OpenClaw would be a redundant layer.
- **WhatsApp Business API cost and compliance.** Meta's WhatsApp Business API has per-message costs and requires verified business registration — non-trivial for a charity. This is independent of OpenClaw.
- **Accessibility assumption.** It is not verified that WhatsApp is more accessible for macular degeneration patients than the web app. The web app is purpose-built with WCAG 2.1 AA, screen reader support, and voice input. WhatsApp is generic.

## Promising direction

**Direction B** — build a direct WhatsApp integration if channel diversification is the goal, skipping OpenClaw entirely.

OpenClaw's viral popularity doesn't translate to meaningful wins here. The project already has an agent loop, voice pipeline, and session management. OpenClaw's primary value — the messaging gateway — can be achieved more reliably via Twilio or the WhatsApp Business API directly, without the governance risk of a fast-moving open-source project. The only genuine question this exploration surfaces is whether WhatsApp is a worthwhile _channel_ for users — and that is a product question, not an OpenClaw question.
